# 1. 本次修改的目标与边界

本次工作不以“完整重构一台轮腿机器人”为目标，也不要求先实现论文后续的离地检测、跳跃、自恢复、复杂地形估计或完整整车功率管理。当前唯一主目标是：

**在现有 `Final-Code` STM32/FreeRTOS 工程上，把论文图16从传感器/电机反馈一直打通到 2 个轮电机 + 4 个关节电机共 6 个电机的期望力矩输出，并能够在实机上逐阶段闭环验证。**

最终软件闭环必须严格对应下面这条链路：

```text
                    ┌──────────── 参考输入 ────────────┐
                    │ x_d / ψ_d / Ld_l,Ld_r / γ_d    │
                    └─────────────────────────────────┘
                                      ↓
BMI088 + 2×轮电机反馈 + 4×关节电机反馈
                  ↓
          五连杆运动学 / 状态估计器
                  ↓
      ┌───────────┼────────────┬─────────────┐
      ↓           ↓            ↓             ↓
  LQR K(L0)   转向PD      双腿协调PD     腿长PID+前馈
   → T,Tp      → ΔT          → ΔTp          → Fl0,Fr0
      │           │            │             │
      │           │            │        横滚补偿 Kγ
      │           │            │          → ΔFγ
      ↓           ↓            ↓             ↓
  Tl/Tr       Tp_l/Tp_r             Fl/Fr
      │           │                   │
      │           └─────────┬─────────┘
      │                     ↓
      │                左右腿 VMC
      │         [F,Tp] → Jᵀ[F,Tp] → 4关节力矩
      │                     │
      └──────────────┬──────┘
                     ↓
       2轮电机力矩 + 4关节电机力矩
                     ↓
                 非线性机器人
                     ↓
                   反馈
```

论文图16对应的最终控制量为：

```text
左轮力矩      T_l
右轮力矩      T_r
左腿关节1     τ_l1
左腿关节2     τ_l2
右腿关节1     τ_r1
右腿关节2     τ_r2
```

当前阶段**不做**：论文第3章离地检测、空中姿态策略、跳跃控制、侧翻自恢复；云台和发射机构只保证原代码不被无意破坏，不参与本次轮腿控制闭环。

# 2. 现有 `Final-Code` 的真实基础，以及本次应该如何利用

现有仓库并不是空工程，因此不应该重新从 CubeMX 建工程。当前工程已经具备本项目需要的大部分底层基础：

- MCU：STM32F407IGH6，168 MHz；
- FreeRTOS/CMSIS-RTOS v1；
- CAN1、CAN2，均为 1 Mbps；
- BMI088：SPI1 + DMA + DRDY 中断；
- Mahony 姿态解算；
- `Task/chassis_task.c`：现有底盘高优先级任务，按 1 ms 周期运行；
- `Task/ins_task.c`：IMU 实时任务；
- `Task/control_task.c`：VTM/遥控输入解析；
- `User/Middleware/drv_CAN_receive.c`：现有 DJI 电机 CAN 接收与发送；
- `User/Algorithm/alg_pid.c/.h`：现有 PID；
- `Task/calibrate_task.c`：现有姿态/PID 清零入口。

## 2.1 最重要的架构决定：保留 `CHASSIS_TASK`，重写其内部逻辑

上一版计划建议新增独立 `wheel_leg_task`。重新结合当前仓库后，**不建议为了图16再新增一个新的 FreeRTOS 控制任务**。

原因是现有 `Task/chassis_task.c` 已经：

```c
const portTickType xFrequency = 1;
...
osDelayUntil(&xLastWakeTime, xFrequency);
```

也就是说它本身就是一个适合承担轮腿主控制器的 1 kHz 高优先级周期任务。最小侵入方案是：

- 保留 `CHASSIS_TASK()` 函数名；
- 保留 `freertos.c` 里的任务创建方式；
- **删除 `chassis_task.c` 中原四麦轮逆运动学、四轮速度 PID、云台坐标转换；**
- 把 `CHASSIS_TASK()` 改成论文图16的顶层调度器；
- 复杂算法放在 `User/WheelLeg/` 中，`chassis_task.c` 只负责按顺序调用。

这样不用修改 CubeMX 任务表，也不会额外引入调度关系。

## 2.2 原 `chassis_task.c` 中明确要删除/停用的旧逻辑

以下逻辑属于四麦轮底盘，不应继续参与轮腿控制：

```text
chassis_wheel_inverse_resolution()
gimbal_coordinate_resolution()
四个 chassis[] 轮速 PID
WHEEL_TO_CORE_DISTANCE
旧 GEAR_RATIO
原四麦轮 wheel_target_omega[4]
output_map() 中固定 ×819.2 的映射
由 yaw 云台编码器计算底盘坐标 theta 的逻辑
```

遥控器 `key` 仍然保留，但由新的“参考输入生成器”读取，不能直接继续复用旧麦轮速度映射。

# 4. 统一数据结构：先定义“图16里到底有哪些量”

建议在 `wheel_leg_types.h` 中先定义完整数据流，不要边写算法边临时加全局变量。

## 4.1 电机层

```c
typedef struct {
    float rotor_pos_rad;
    float rotor_vel_rad_s;
    float output_pos_rad;
    float output_vel_rad_s;
    float current_A;
    float torque_Nm;
    uint32_t last_rx_tick;
    uint8_t online;
} WheelMotorState;

typedef struct {
    float pos_rad;       // 输出轴机械角，已经过零位和方向映射
    float vel_rad_s;
    float torque_Nm;
    float temperature_C;
    uint32_t last_rx_tick;
    uint8_t online;
} JointMotorState;
```

## 4.2 单腿运动学状态

```c
typedef struct {
    float q1;
    float q4;
    float dq1;
    float dq4;

    float L0;
    float theta;
    float dL0;
    float dtheta;

    float phi_bc;       // 论文1.6中的轮电机定子固定基座 c 相对机体 b 的角度
    float dphi_bc;

    float J[2][2];      // [L0, theta] 对 [q1, q4] 的 Jacobian
    float detJ;
} LegKinematicState;
```

这里必须特别增加 `phi_bc/dphi_bc`。论文速度解算不是只用 `theta_dot`，而是明确使用轮电机定子固定基座 `c` 相对机体 `b` 的角速度 `φ̇_bc`。因此五连杆模块除了输出 `L0、theta、J`，还必须输出这一杆件的姿态/角速度。

## 4.3 图16估计器输出

```c
typedef struct {
    float L0_l;
    float L0_r;
    float theta_l;
    float theta_r;

    float L0;           // LQR调度使用的等效腿长
    float theta;        // LQR使用的等效腿角
    float dtheta;

    float xb;
    float dxb;

    float phi;          // body pitch, rad
    float dphi;         // body pitch rate, rad/s

    float yaw_rate;     // 图16中的 ψ_hat，按论文文字解释为航向角速度
    float roll;         // 图16中的 γ_hat

    float x[6];         // [theta,dtheta,xb,dxb,phi,dphi]^T
} WheelLegEstimate;
```

## 4.4 参考输入

```c
typedef struct {
    float v_d;
    float x_d;
    float yaw_rate_d;   // ψ_d
    float Ld_l;
    float Ld_r;
    float roll_d;       // γ_d
    float x_ref[6];
} WheelLegReference;
```

## 4.5 控制器中间输出

```c
typedef struct {
    float T;
    float Tp;

    float dT_yaw;
    float T_l;
    float T_r;

    float dTp_sync;
    float Tp_l;
    float Tp_r;

    float F_l_base;
    float F_r_base;
    float dF_roll;
    float F_l;
    float F_r;

    float tau_l[2];
    float tau_r[2];
} WheelLegControlOutput;
```

这样日志可以直接把图16每个方框之间的信号都打印出来，调试时能够判断到底是估计器错、LQR错、辅助控制器错，还是 VMC 错。

# 5. Phase 1：先改 CAN，使 6 个执行器能够“读状态 + 发力矩”

这是第一项实际代码工作。

## 5.1 两个 M3508+C620 轮电机

现有 `drv_CAN_receive.c` 已能解析 DJI 电机反馈：

```text
ecd
speed_rpm
given_current
temperature
```

且 `CAN_cmd_chassis()` 已能通过 `0x200` 一次发送四路 C620 命令。因此短期不需要重新写底层 HAL CAN。

建议：

1. CAN2 保留 C620；
2. 只使用 `0x201、0x202` 两个反馈 ID；
3. `CAN_cmd_chassis(cmd_l, cmd_r, 0, 0)` 即可先控制两个轮子；
4. 新建 `wheel_motor.c` 做单位转换，而不是让 LQR 直接接触 `ecd/rpm/int16_t current_cmd`。

需要完成：

```text
speed_rpm → motor rotor rad/s
motor rotor rad/s / gear_ratio → wheel relative stator rad/s
ECD 单圈展开 → rotor accumulated angle
wheel torque T [N·m] → current/current_cmd
```

最后一项必须通过参数文档中的 C620 扭矩换算进行标定/核实。

## 5.2 四个 DM-J8009P-2EC 关节电机

当前 `Final-Code` 中没有可直接使用的 DM-J8009P-2EC 驱动，历史中的 `8115can.c` 实际为空文件，因此这一层必须新写。

`dm_joint_motor.c` 至少实现：

```text
DM_Enable(id)
DM_Disable(id)
DM_SendMITTorque(id, tau)
DM_ParseFeedback(...)
DM_GetState(index)
```

图16最终只需要关节力矩，所以 bring-up 以后最核心模式为：

```text
MIT mode
kp = 0
kd = 0
t_ff = τ_joint
```

但发送打包/反馈解包必须严格按照当前 DM-J8009P-2EC 手册中的 `PMAX/VMAX/TMAX` 和量化范围实现，不可照搬其他达妙型号。

## 5.3 修改 `HAL_CAN_RxFifo0MsgPendingCallback`

当前回调集中在 `drv_CAN_receive.c`。建议不再创建第二套 HAL 回调，而是在现有回调中分发：

```c
if (CAN2) {
    parse_dji_wheel_motor(...);
}

if (CAN1) {
    if (is_dm_feedback(id)) {
        DM_ParseFeedback(...);
    }
    // 其他旧步兵设备在本阶段不参与控制

```

# 6. Phase 2：把 BMI088 变成“图16能直接使用的机体状态”

原 `ins_task.c` 可以保留，重点是补一个稳定的输出接口。

## 6.1 不能直接拿当前 `mahony.PITCH/ROLL` 填 LQR

当前 `Get_Angle1()` 输出：

```text
YAW/PITCH/ROLL 单位 = degree
```

而论文状态空间、LQR、VMC 全部使用 rad。因此新增：

```c
typedef struct {
    float pitch_rad;
    float roll_rad;
    float yaw_rad;
    float gyro_body_rad_s[3];
} INSSnapshot;

void INS_GetSnapshot(INSSnapshot *out);
```

在 getter 中统一做：

```text
degree → rad
IMU frame → body frame
零位偏置
轴方向符号
```

## 6.2 角速度必须避免误用 `mahony.g`

当前 `INS_TASK` 在 Mahony 更新前把滤波后的 gyro 放进：

```c
mahony.g[i]
mahony.g_smc[i]
```

但 `MahonyAHRSUpdateIMU()` 内部会继续修改 `mahony.g[]`，包括反馈校正以及乘以 `0.5*dt` 参与四元数积分。因此 **Mahony 更新结束后的 `mahony.g[]` 不能再被当作原始 rad/s 角速度直接送进 LQR**。

建议 getter 使用：

```text
mahony.g_smc[]
```

或单独保存 `GYRO.Out[]` 快照，作为机体系角速度输入。

## 6.3 图16本阶段需要的 IMU 量

```text
phi      = 机体 pitch [rad]
dphi     = 机体 pitch rate [rad/s]
gamma    = 机体 roll [rad]
psi_hat  = 航向角速度 / yaw rate [rad/s]
```

论文图16的 `ψ_d` 在正文中定义为**期望航向角速度**，因此转向控制当前不需要无磁力计 yaw 绝对角长期稳定；需要可靠的是 yaw rate。

# 7. Phase 3：实现五连杆正运动学、Jacobian，以及速度解算额外需要的 `phi_bc`

这是整个项目最关键的数学模块之一。

## 7.1 输入

每条腿输入两个主动关节输出轴角：

```text
q = [φ1, φ4]^T
qdot = [φ̇1, φ̇4]^T
```

必须先经过：

```text
DM raw position
→ mechanical zero offset
→ joint direction sign
→ paper coordinate φ1/φ4
```

## 7.2 输出

每条腿至少输出：

```text
L0
θ
dL0
dθ
J = ∂[L0, θ] / ∂[φ1, φ4]
phi_bc
dphi_bc
```

其中：

```text
[dL0, dθ]^T = J [dφ1, dφ4]^T
```

因此只要 DM 的关节速度可靠，就优先用 Jacobian 直接得到 `dL0/dtheta`，不要先用 1 ms 差分角度再放大噪声。

## 7.3 Jacobian 的用途有两个

第一处用于运动学速度：

```text
qdot → [dL0,dtheta]
```

第二处用于 VMC：

```text
τ_joint = J^T [F,Tp]^T
```

这两个用途必须共用同一个 J 和同一套坐标定义，不能各写一套公式。

## 7.4 `phi_bc` 必须单独建模

论文1.6速度解算中使用：

```text
ω = ω_eb + φdot_bc + ω_ecd
```

其中 `c` 是“驱动轮电机定子固定基座（五连杆从动杆）”。因此要从实际 SolidWorks 结构确定：

- 哪一根五连杆构件是 `c`；
- 它对应论文 φ2/φ3 或实际哪一个杆件角；
- 左右腿镜像后符号如何变化。

这不是可随意假设的量，已在参数文档中升级为图16关键 P0/P1 项。

## 7.5 PC 单元测试

不要直接在 STM32 上验证公式。先写 Python 参考实现：

```text
给定100~1000组合法关节角
→ FK 得 L0/theta/phi_bc
→ 数值微分得到 J_num
→ 与解析/STM32公式 J 对比
```

还要验证虚功：

```text
τ^T dq ≈ [F,Tp]^T dx
```

并用论文 1.2.3 的静力学闭式公式作为第二套 VMC 结果交叉检查。

## 7.6 Phase 3 验收条件

```text
[ ] CAD中至少10个典型姿态 FK 与程序一致
[ ] 左右腿镜像后 L0/theta 物理意义一致
[ ] J 与数值差分一致
[ ] J^T VMC 与静力学公式在非奇异区一致
[ ] phi_bc/dphi_bc 与CAD运动方向一致
[ ] 能识别接近奇异位形
```

# 8. Phase 4：按照论文1.6实现状态估计器

这一阶段的目标是生成 LQR 需要的：

```text
x = [theta, dtheta, xb, dxb, phi, dphi]^T
```

同时输出图16其他控制器需要的 `theta_l/theta_r、L0_l/L0_r、yaw_rate、roll`。

## 8.1 左右腿的等效状态

论文图16同时画出了左右腿状态，但 LQR 使用的是单个 6 维状态。因此当前实现建议明确采用：

```text
L0     = (L0_l + L0_r) / 2
theta  = (theta_l + theta_r) / 2
dtheta = (dtheta_l + dtheta_r) / 2
```

这是工程实现约定，论文没有在图16正文中逐项明确“平均”的公式，因此必须在参数文档中标记为 ASSUMED，并允许后续根据实机修改。

## 8.2 轮子对地速度不能直接使用 `speed_rpm × R`

论文明确指出：电机编码器测得的是转子相对定子的角速度，而 LQR 需要轮子相对惯性系的运动。

每侧按论文1.6做：

```text
ω_e      = C620 rotor speed / gear_ratio
ω_eb     = IMU得到的机体相对大地俯仰角速度
φdot_bc  = 五连杆运动学得到的轮电机定子基座相对机体角速度

ω_ground = ω_eb + φdot_bc + ω_e
v_wheel  = R * ω_ground
```

注意：上述加减号必须通过最终坐标系和左右轮镜像方向验证，代码中不要把符号散落在公式里，应由 `hardware_map.h` 的方向参数统一处理。

## 8.3 机体平动速度

论文给出：

```text
xb_dot = ω_ground R
       + L0 dtheta cos(theta)
       + dL0 sin(theta)
```

分别对左右侧解算后，当前实现取平均：

```text
dxb = 0.5 * (dxb_l + dxb_r)
```

## 8.4 机体位置 xb

控制启动时：

```text
xb = 0
xd = 0
```

运行中：

```text
xb += dxb * dt
```

这是相对位置，不需要世界坐标绝对定位。进入 BALANCE 前同时将 `xd` 对齐当前 `xb`，避免使能瞬间位置误差产生大力矩。

后续若发现积分漂移影响长时间运行，再增加轮角位置辅助；第一版不要过度复杂化。

## 8.5 Phase 4 验收条件

输出关闭、手动推动机器人：

```text
[ ] dxb 方向与实际推动方向一致
[ ] 静止时 dxb 接近0
[ ] 抬腿改变关节但轮子不滚动时，不应被错误解释成同等大小的底盘平移
[ ] 左右侧独立 dxb 量级接近
[ ] x[0..5] 全部是 SI 单位
```

# 11. Phase 7：实现图16三个辅助控制环

这三个控制器不要混进 LQR 文件。

建议统一放在 `auxiliary_controller.c`。

## 11.1 转向 PD

论文：

```text
e_ψ = ψ_d - ψ_hat
ΔT_yaw = PD(e_ψ)
```

然后：

```text
T_l = T - ΔT_yaw
T_r = T + ΔT_yaw
```

符号以图16为初始定义，最终由实机坐标约定确认。

## 11.2 双腿协调 PD

论文定义：

```text
e_theta = theta_r - theta_l
ΔTp_sync = PD(e_theta)
```

然后：

```text
Tp_l = Tp - ΔTp_sync
Tp_r = Tp + ΔTp_sync
```

这个控制器的作用不是控制机体 pitch，而是防止转向时左右腿向相反方向摆开。

## 11.3 腿长 PID + 重力前馈

每条腿独立：

```text
e_L_l = Ld_l - L0_l
e_L_r = Ld_r - L0_r

F_l_base = PID_l(e_L_l) + F_ff_l
F_r_base = PID_r(e_L_r) + F_ff_r
```

现有 `alg_pid.c` 的 `K_F` 不能直接当论文这里的“重力前馈”，因为当前代码中的 `K_F` 实际计算的是：

```c
(Target - Pre_Target) * K_F
```

这是目标变化前馈，不是静态重力补偿。因此：

- 腿长反馈部分可以复用 `PID_t`；
- **重力前馈必须单独写成 `F_ff` 加法项。**

论文没有给出具体的重力前馈解析公式，所以第一版应根据真实整机质量/腿姿态建立静态支持力模型，或者先将 `F_ff` 做成可配置量进行台架标定；不要在文档中伪造“论文公式”。

## 11.4 横滚补偿

论文图16是：

```text
e_gamma = gamma_d - gamma_hat
ΔF_roll = K_gamma * e_gamma
```

然后：

```text
F_l = F_l_base - ΔF_roll
F_r = F_r_base + ΔF_roll
```

这里是**比例补偿 Kγ**，当前计划不应再写成“横滚 PID/PD”。

# 12. Phase 8：实现 VMC，把每条腿的 `[F,Tp]` 变成两个关节力矩

对左腿：

```text
w_l = [F_l, Tp_l]^T
τ_l = J_l^T w_l
```

对右腿：

```text
w_r = [F_r, Tp_r]^T
τ_r = J_r^T w_r
```

得到：

```text
τ_l1, τ_l2, τ_r1, τ_r2
```

## 12.1 VMC实现注意事项

1. `J` 必须与五连杆 FK 使用同一坐标定义；
2. `F` 单位为 N；
3. `Tp` 单位为 N·m；
4. 关节输出必须为 N·m；
5. 接近奇异位形时禁止直接放大输出；
6. 左右腿镜像方向只能在 `hardware_map.h` 做一次，不得在 VMC 公式里“补符号”。

## 12.2 静力学公式只作为验证，不建议另写一套正式控制器

论文1.2.3给出了静力学闭式解。建议 Python 侧/单元测试用它验证 `J^T`，正式 STM32 控制只保留一套 VMC 实现，避免两套公式长期漂移。

# 14. `CHASSIS_TASK()` 最终应该长什么样

最终 `Task/chassis_task.c` 不再包含复杂数学公式，主循环建议固定为：

```c
void CHASSIS_TASK(void const *argument)
{
    uint32_t last_wake = osKernelSysTick();

    WheelLeg_Init();

    while (1)
    {
        // 1. 读取一致的传感器/电机快照
        WheelLeg_ReadMotorSnapshot();
        INS_GetSnapshot(&ins);

        // 2. 两条腿运动学
        FiveBar_Update(LEFT,  ...);
        FiveBar_Update(RIGHT, ...);

        // 3. 状态估计，得到论文的 x 和图16其他估计量
        StateEstimator_Update(..., &estimate);

        // 4. 由遥控/测试量得到 x_d, ψ_d, Ld, γ_d
        ReferenceGenerator_Update(&key, &estimate, &reference);

        // 5. LQR → T, Tp
        LQR_Calculate(&estimate, &reference,
                      &ctrl.T, &ctrl.Tp);

        // 6. 图16三个辅助环
        YawPD_Calculate(..., &ctrl.dT_yaw);
        LegSyncPD_Calculate(..., &ctrl.dTp_sync);
        LegLength_Calculate(...,
                            &ctrl.F_l_base,
                            &ctrl.F_r_base);
        RollComp_Calculate(..., &ctrl.dF_roll);

        // 7. 合成左右 T / Tp / F
        WheelLeg_CombineVirtualCommands(&ctrl);

        // 8. VMC → 四关节扭矩
        VMC_Calculate(..., ctrl.tau_l, ctrl.tau_r);

        // 9. 最小有效性检查、限幅
        WheelLeg_CheckAndLimit(...);

        // 10. 六电机输出
        WheelLeg_SendOutputs(...);

        // 11. 降采样日志
        WheelLeg_Log(...);

        osDelayUntil(&last_wake, 1);
    }
}
```

**执行顺序不要随意改变。** 图16所有反馈都必须来自同一周期的状态快照，不能一部分用新数据、一部分用上一个周期。

# 15. FreeRTOS与控制周期安排

## 15.1 建议第一版统一按 1 kHz

理由不是凭空选择，而是现有代码已经基本按 1 ms 体系设计：

- `CHASSIS_TASK()` 当前就是 `osDelayUntil(...,1)`；
- `PID_t.D_T` 当前固定为 `0.001f`；
- Mahony 初始化 `dt=0.001f`；
- BMI088 gyro 配置为 1 kHz 级数据率；
- C620 默认反馈链路也适合高频更新。

因此上一版文档中“主控制 500 Hz / dt=0.002 s”的假设应取消。第一版直接采用：

```text
INS nominal update    1 kHz
Wheel-leg main loop   1 kHz
Control dt            0.001 s
```

这里的 1 kHz 是主控制任务节拍，不是要求四台 DM 都各自 1 kHz 发命令和反馈。Phase 1 的 DM 调度采用左右腿交错，每台 500 Hz；1 kHz 中间周期复用最近一次完整快照。C620 轮电机仍按 1 kHz 发送双轮命令。

后续只有在实测 CPU/CAN 无法满足时再降频，而不是一开始额外引入 500 Hz/1 kHz 双周期问题。

## 15.2 任务关系

建议继续：

```text
INS_TASK       Realtime
CHASSIS_TASK   High
CONTROL_TASK   High
```

其中 `CONTROL_TASK` 只是低计算量遥控解析；真正控制全部在 `CHASSIS_TASK`。

# 19. 当前代码中需要特别注意的 8 个具体问题

1. **`chassis_task.c` 是旧四麦轮算法，必须整体替换控制逻辑，而不是在后面追加 LQR。**
2. **Mahony 的 `PITCH/ROLL/YAW` 当前是度，不是 rad。**
3. **`mahony.g[]` 在 Mahony 更新内部被修改，不能在更新后直接当 gyro rad/s；应使用 `g_smc` 或独立 gyro snapshot。**
4. **现有 `PID_t.D_T` 固定 0.001 s，因此主轮腿控制第一版应与现有 1 kHz 对齐。**
5. **现有 PID 的 `K_F` 不是重力前馈，不能直接拿来实现论文腿长“PID + 前馈”。**
6. **原 `output_map(*=819.2)` 只是旧 C620 控制量映射，不能继续作为轮端 N·m→电流转换。**
7. **论文速度估计需要 `phi_bc_dot`，只有 `L0/theta` 不够。**
8. **论文自身对 `x_ref[3]` 的写法存在两种口径（0.5·v_d 与 0），实现必须参数化而不是默默选一个。**

```text
five_bar.c：FK、中心差分 Jacobian、L0/dL0、body leg axis、phi_bc proxy
        ↓
wheel_leg_state_estimator.c：theta_world、dtheta、xb/dxb、phi/dphi、yaw/roll
        ↓
wheel_leg_lqr.c：论文固定名义 K（R22=0.25，占位）
        ↓
wheel_leg_auxiliary.c：转向、双腿协调、腿长 PID+FF、横滚差分
        ↓
wheel_leg_vmc.c：每腿 tau = J^T[F,Tp]
        ↓
wheel_leg_safety.c：DISABLED / ACTIVE / FAULT 最小安全门
        ↓
WheelLegMotorIO
```

这条链已经在 `CHASSIS_TASK` 的 1 kHz 主循环中连通。IMU 任务在 Mahony 更新完成后发布 SI 单位快照；所有控制模块均保留独立的有效性标记。辅助环默认参数和 `phi_bc` 都是软件占位，不代表实机增益或最终机械定义。

PC 侧新增 `tools/wheel_leg/five_bar_reference.py` 与 `solve_lqr_schedule.py`。前者用于 FK/Jacobian/虚功交叉核对，后者只接受外部提供的 `A(L0),B(L0)`，按 `R=diag(1,0.25)` 求解并生成 C 表，不会替 CAD 或质量参数做猜测。

安全边界保持不变：`WL_ACTUATION_COMPILED=0` 时真实输出始终为零；旧云台/发射 CAN 发送默认关闭；任一电机快照过期、DM 报错、IMU 过期、五连杆无解或 Jacobian 接近奇异时，VMC 输出无效并提交零力矩。只有完成 CAD/零位/方向/IMU 安装/质量参数核实后，才允许继续做 `K(L0)` 调度和实机增益标定。

# 24. 按计划书逐项核对的剩余工作（2026-08-09）

## 已落地的软件部分

- Phase 1 的 C620/DM 编解码、六电机快照、CAN ID 分发、左右腿交错 DM 调度和默认零输出门控；
- BMI088/Mahony 的角度单位转换、`g_smc` 角速度快照和超时接口；
- 五连杆假设模型的 FK、数值 Jacobian、`body/world` 角分离、`phi_bc` 显式 proxy；
- 论文六状态估计、轮子对地速度组合、参考生成、固定名义 LQR、辅助环接口、VMC 和最小 `DISABLED/ACTIVE/FAULT` 门；
- `CHASSIS_TASK` 的 1 kHz 主链和主机侧回归测试。

## 尚未完成或只能算“部分完成”的项目

1. **真实机械核对**：CAD 五连杆尺寸、左右镜像、DM 零位/方向、轮半径/减速比、实际 `phi_bc` 杆件和 IMU 安装轴向仍未确认；当前代码使用 A96~A102 占位。
2. **真实驱动标定**：C620 扭矩—电流关系、DM 输出轴反馈含义、六电机小力矩方向和在线验收尚未在实机完成。
3. **动态 LQR**：目前只有论文 `R=diag(1,0.25)` 的固定名义 K；尚未用真实 CAD 质量/质心/惯量生成 `A(L0),B(L0)`、多项式/查表 `K(L0)` 和 STM32 运行时调度。
4. **辅助环实机参数**：转向 PD、双腿协调 PD、腿长 PID、横滚 `Kγ` 和重力前馈默认全为零软件占位；尚未确定任何实机增益或重力模型。
5. **VMC 交叉验证**：`J^T` 已实现，但论文静力学闭式公式与 CAD 典型姿态的交叉验证尚未完成。
6. **参考输入**：当前只接入键盘 W/S/A/D 的软件测试映射；模拟摇杆、拨轮腿长、遥控有效性/超时和正式使能流程尚未接入。
7. **保护与日志**：反馈过期、姿态限幅和 Jacobian 门已存在，但 `WL_CONTROL_COMMAND_TIMEOUT_MS`、`WL_MAX_CAN_TX_ERRORS` 尚未形成锁存动作，温度保护、Bus-Off处理、100~200 Hz 图16节点日志也尚未完成。
8. **实机阶段验收**：计划中的 Stage A 方向核对以及 Stage D~J（支架腿长环、固定腿长平衡、协调/横滚/转向/速度、最终 K(L0)）均未执行；当前只能称为“软件链打通”，不能称为“机器人已完成图16闭环”。
9. **工程构建**：当前已做 GCC 主机编译/测试，尚未在 Keil/ARMCC 和真实 STM32 板上完成构建、下载与上电验证。
